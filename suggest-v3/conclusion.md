# Итоговые варианты и вывод

## Вопрос

Итоговые варианты:
1. Nested SwiftUI ScrollView = undefined behavior из-за iOS версий
2. 1 SwiftUI ScrollView и внутри 3 HStack с offset'ами = много вызовов @Published для автоскролла

Как будто это единственные претенденты которые были бы логичны, но не заработали. Или были упущены неплохие претенденты?

## Ответ

Это два главных претендента которые логично напрашиваются:

1. **Nested ScrollView** — логичная идея (parent для юзера, children для авто-скролла), но undocumented behavior
2. **Один ScrollView + .offset()** — логичная идея (один скролл, SwiftUI делает остальное), но @Published 60-120 раз/сек убивает CPU

Из того что не пробовали, но могло бы прийти в голову:

3. **UICollectionView + compositional layout с orthogonal scrolling** — каждая секция скроллится независимо. Но для авто-скролла на разных скоростях всё равно нужен CADisplayLink + contentOffset, то есть по сути тот же point3, только через более тяжёлый API
4. **UIViewRepresentable вместо Introspect** — те же ~300 строк behavior + теряется декларативная раскладка чипов. Больше кода за ту же функциональность

Ни один из них не предлагает принципиально другого решения. Задача "разные скорости авто-скролла по строкам" в итоге **требует** отдельный contentOffset на строку, а плавная анимация **требует** обходить SwiftUI state system. Point3 (несколько UIScrollView через Introspect) — самый прямой путь к обоим требованиям.
